# Release docs sync

Two documentation layers exist and only one maintains itself. The Terraform
Registry reference (`docs/`) is generated by tfplugindocs and CI fails if it
drifts — never hand-sync it. The **narrative docs** at docs.barndoor.ai
(repo `barndoor-ai/docs`, `terraform/` directory) encode provider capabilities
in prose and tables, and nothing fails when the provider outgrows them. This
skill keeps that second layer honest, release by release.

## Why this runs at release time, not per PR

docs.barndoor.ai publishes to production the moment a PR merges to `main`
(Mintlify GitHub App). Documenting an unreleased feature therefore misleads
users, and provider releases sometimes wait on platform releases (BCP-3630's
directory data sources waited for bdai-platform #6794). The release is the
only moment "what can users actually do?" changes, so the docs question is
answered once, here.

## Step 1: Classify the delta

Walk the `Unreleased` section of `CHANGELOG.md` (everything since
`git describe --tags --abbrev=0`). For each entry:

| Change | Product-docs work |
| --- | --- |
| New resource or data source | **Always.** Index tables at minimum; check whether a guide flow, a "Before You Begin" prerequisite, or the portal-only framing changes |
| Behavior change the narrative docs state (retry, import IDs, destroy semantics, validation timing, defaults) | **Yes** — find the stated claim and fix it (Step 2 lists where claims live) |
| New attribute on an existing resource | Usually no — the Registry reference covers it. Yes only if it changes a documented workflow |
| Bug fix, dependency bump, CI/tooling | No |

Do not trust memory of what the docs say — grep them. The claims worth money
are the negative ones ("Terraform can't…", "must be copied from the app",
"no client-side retry"): new features exist precisely to falsify those.

## Step 2: The docs surfaces that encode provider capabilities

All paths in `barndoor-ai/docs`:

- `terraform/index.mdx` — per-product-area **resource tables** and data-source
  lines; the **"When to use Terraform"** portal-only list; the version-pin
  snippet.
- `terraform/getting-started.mdx` — provider env-var table, first-resource
  example, troubleshooting accordions.
- `terraform/manage-mcp-access.mdx`, `terraform/llm-gateway.mdx`,
  `terraform/data-protection.mdx` — guide flows and their **"Before You
  Begin"** prerequisites. These state what must be fetched from the app;
  new data sources routinely falsify them.
- `terraform/best-practices.mdx` — **import-ID table**, **destroy-semantics
  table**, "Plans that look like drift", troubleshooting entries.

The version pin shown in docs (`~> 0.x`) floats across minor releases —
bump it only for a new major.

## Step 3: Sequence against the publish

1. Prepare the docs PR while the release is in flight. **Do not merge it.**
2. Tag and publish per [RELEASING.md](../../../RELEASING.md); complete its
   Verify section (version live on the Registry, `terraform init` smoke test).
3. Re-run the example checks below against the *published* version, then
   merge the docs PR.

## Step 4: Testing bar for doc examples

Every new or changed HCL snippet in the docs PR:

- Assemble the page's snippets into a standalone config directory.
- `terraform init` against the published version (this also proves the pin
  resolves), then `terraform validate` and `terraform fmt -check`.
- Pre-publish, run the same checks against the local build via
  `make dev-install` + a `dev_overrides` CLI config — then repeat against the
  Registry after the tag.
- Substantive new flows additionally get a live `apply` → re-`plan` (expect
  empty diff) → `destroy` against the disposable dev acceptance org (the same
  environment `nightly-acceptance.yml` uses). Never the protected org, and
  never mint a new provider credential — one is active per org and the
  nightly owns it.
- Record the per-example matrix (validate / apply / re-plan / destroy) in the
  docs PR description.

This bar is not ceremony: an example with invalid HCL shipped in a release
once (fixed in 0.2.0, now guarded by `make validate-examples`), and live
testing caught the `tools/call:` actions-format bug before the docs section
launched.

## Worked example: v0.4.0 (BCP-3630)

Delta: `barndoor_dlp_detection_engine` resource + data source; data sources
for `llm_provider`, `mcp_server_directory`, `agent_directory`; client retry
with backoff; plan-time validation of policy rule actions.

- `index.mdx`: one new resource row (Data Control Center) and four new
  data-source mentions across three product areas.
- `data-protection.mdx`: "Before You Begin" required a Protection Profile ID
  copied from the app → the guide now manages or looks up the engine itself.
- `manage-mcp-access.mdx`: "directory entry ID … visible in the Barndoor app"
  → directory data-source lookups.
- `best-practices.mdx`: the "no client-side retry" troubleshooting claim
  became false and was removed; plan-time validation changed where the
  actions-format error surfaces.
- The connection import.sh and example-validation CI fixes: Registry-only,
  no product-docs work — correctly classified as "no".

## Mechanics

- The docs repo checkout must be in the session (usually
  `../docs` next to this repo); ask for it if absent.
- Docs repo conventions: one topic branch per change, PR to `main`, and its
  `AGENT.md` forbids AI attribution in commit messages.
